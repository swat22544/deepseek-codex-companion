# 时间预算、进展与超时处理

本机制从 **1.0.3 / `2026-10-13-adaptive-timeouts`** 开始使用。主代理为本次工作选择范围和预算，运行器按实际材料自动给出默认值；DeepSeek 不能修改自身时限。时间预算独立于固定 Flash / Max、文件范围、工具次数、候选写入限制和最终验收，这些约束仍然生效。

**1.0.4** 将中、大任务的默认总时限从 15/30 分钟提高为 **20/45 分钟**；小任务、无进展时限及显式 60 分钟上限不变。更改适用于新启动的调用，不追改历史预算或改变已经运行的任务。

**1.1.0** 将相同预算规则用于 Harness 和 OpenCode。并行调用各自计时，任务 A 的输出和监看活动不会重置任务 B 的无进展时限；一条超时也不能自动重启或转派另一后端。

## 自动预算

省略所有时间字段，或只写 `"taskSize": "auto"`，即可使用自动分档。

| 规模 | 自动分类条件（按从大到小判断） | 总任务时限 | 无进展时限 |
| --- | --- | --- | --- |
| `large` | 实际快照不少于 8 个，或输入与快照合计不少于 128 KiB | 45 分钟 | 10 分钟 |
| `medium` | 未达大任务条件，且模式为 `inspect/propose`，或输入与快照合计不少于 16 KiB | 20 分钟 | 7 分钟 |
| `small` | 其他情况 | 5 分钟 | 3 分钟 |

`inputBytes` 是 `instruction + input + feedback` 的 UTF-8 字节数，缺少可选反馈时按空文本处理；中文和表情不能按字符数代替字节数。`snapshotBytes` 和 `fileCount` 来自实际建立的不可变快照，使用去重后的文件数量。两者之和用于字节阈值判断，等于阈值即进入较高档位。输入、快照的原有大小上限不变。

规模是估计资源需求的启发式，不是对问题复杂程度或完成时间的预测。材料很短但推理较深的工作，主代理可以显式设置 `"taskSize": "large"`。显式档位优先于自动分类，显式毫秒时限再优先于档位默认值；这些选择会写入结果，便于复核。

## 显式预算与旧字段

下列字段放在正常委派请求的顶层，单位均为毫秒：

```json
{
  "taskSize": "large",
  "totalTimeoutMs": 2700000,
  "idleTimeoutMs": 900000
}
```

该片段选择大任务，并显式给出 **45 分钟总时限、15 分钟无进展时限**；它不是完整请求，仍需提供 `taskType/instruction/input` 等必要字段。

- `totalTimeoutMs`、`idleTimeoutMs`、旧 `timeoutMs` 必须是 1000–3600000 范围内的安全整数；最长 60 分钟，不能填写 `null`、数字字符串、非整数、`NaN` 或无限值。
- `timeoutMs` 继续表示显式总时限，没有被忽略或废弃。若同时提供 `totalTimeoutMs`，两者必须相等，否则拒绝请求。
- 省略无进展时限时，运行器取该档默认无进展时限与最终总时限的较小者。例如旧请求 `timeoutMs: 180000` 最多只允许三分钟运行。
- 显式 `idleTimeoutMs` 超过最终总时限时拒绝请求，不会擅自替用户缩短或增加预算。
- 显式 `taskSize` 不会覆盖显式时间字段，也不会改变权限模式。

要迁移旧的三分钟请求，在**新请求**中删除 `timeoutMs` 以启用自动分配，或把显式总时限改为合适值；若新旧总时限字段同时存在，应同步修改或只保留一个。不要为了让历史记录符合新设置而修改已归档请求和结果。每次反馈续作都是独立新调用，主代理应重新判断范围与预算。

## 两种时钟

**总任务时限**限制一次执行的最长持续时间。运行器完成文件快照、进入后端启动阶段时开始计时；此前的安装与输入文件准备不包含在预算中。调用配置落盘、版本检查、进程启动、模型等待、推理、工具处理和结束后的证据 API 查询都消耗同一份总预算，有进展也不延长它。

**无进展时限**限制自起算点或最近一次可确认进展以来的等待。它与总时限同时运行，任一个到期都会终止本次调用；同一时刻两者都到期时，记录总时限到期。超时后保留清理保护，单次进程终止最多额外等待约七秒；附属 MCP 进程退出检查可能增加少量时间。未确认清理完成则报告失败。

计时采用单调时钟，避免系统日历时间调整补回预算。调度与清理会带来少量结束时间偏差，字段表示允许预算，并不保证子进程恰好在该毫秒退出。

## 什么算作进展

运行器只接受通过当前调用与协议校验的活动：

- 固定 Flash / Max 设置已核对的模型请求开始。
- 当前会话与当前尝试中新产生的输出活动。包含公开文字活动，也包含推理活动的计数和序号等元数据；私有推理文字不写入进展记录或面板。
- 1.1.2 起，OpenCode 还统计具有已核验允许工具身份的参数流增量长度。参数正文不进入审计或面板；缺失、冲突、未知工具及畸形片段不用于续期。Harness 的跨管道缓冲保留压缩后的合法生命周期与活动标记，大量输出不会挤掉 attempt 结束事件。
- 已授权、关联到当前调用的工具开始与工具完成。
- 已核验的最终回复。

模型流的事件需对应当前会话、当前轮次、当前尝试，且序号递增；重复、过期、空输出或不符合协议的事件不能用于续期。工具事件同样不能靠反复重发同一状态无限续期。

**监看面板心跳、HTTP 健康检查、浏览器刷新、日志刷新、普通状态消息都不算模型进展。** 合法进展只重置无进展计时，总时限仍然持续递减。预算已到期后，晚到活动也不能恢复任务。

没有可观察进展可能意味着长时间推理、服务等待、通信异常或停滞，单靠无进展超时不能判断是哪一种。`127.0.0.1` 只是本机运行器/监看服务的地址，不能证明远端模型请求一直正常。反过来，监看记录超过十五秒未更新也只表示可见性中断，不等于模型已经失败；不要以面板心跳替代运行器的进展判断。

## 结果、面板与后续处理

结果 `timing` 包括 `taskSize`、`sizeSource`、`totalSource`、`idleSource`、输入和快照统计、两种时限、经过时间、剩余时间，以及最近进展类别。来源字段为 `auto` 或 `explicit`。无超时时 `timeout` 为 `null`；发生超时时包含 `kind`、`limitMs`、`elapsedMs` 等数值。

面板展示解析后的任务规模、总预算、无进展预算及计时信息，并区分“已达到总任务时限”和“连续一段时间没有可确认进展”。旧运行记录缺少新字段时仍可阅读，不推算或伪造历史预算。

1. 先检查 `timeout.kind`、`timing`、结果中的错误、已返回的内容与 `cleanup`，保留原始证据。
2. 总预算用完时，根据已完成部分决定拆分、接手，或为范围明确的新调用重新分配较长预算。
3. 无进展超时时，检查最后有效活动、服务/登录状态和任务特点。不要直接断言断网，不因超时自动降级模型，也不无条件重试。
4. 清理未确认时先处理残留进程。失败任务留下的候选仍需逐项核验，不作为已完成交付直接应用。

监看服务的可选常驻 watchdog 只保持面板服务可用，不负责继续模型任务，也不延长模型预算。

## 验证范围

预算和进展时钟使用注入时间的单元测试，覆盖超过十分钟的预算、总时限不可延长、无进展重置、重复或无效事件、晚到事件与默认/显式值边界，无需真的等待四十五分钟。虚拟时钟测试证明的是对应计时逻辑，不等于完成了四十五分钟真实模型运行。

2026-10-13 的受控辅助能力评估仍是原来的 12 个初测、2 次复测、1 次续作，仅覆盖当时的 Harness 和模型组合；后续超时与双后端改进不重算原评估分数。OpenCode 的协议、工具、计时和清理需独立验证，不能以相同模型名称继承工具链验收结论。
