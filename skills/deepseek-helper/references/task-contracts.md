# 委派契约与反馈

在需要跨文件分析、机器可读输出或候选实现时读取。这里的“契约”是写进现有 `instruction/input` 字符串的任务要求，不是新增运行器字段；请求字段仍以 [request.md](request.md) 为准。

## 选择值得委派的部分

- **直接用脚本**：条件筛选、去重、排序、精确计算、哈希或格式验证。需要语义判断时可委派分类，再由脚本核对完整输入集合和输出约束。
- **`text`**：已有材料的摘要、局部假设、方案比较或测试思路；提供能支持判断的原文或数据。
- **`inspect`**：指定代码的第二遍审查、跨文件关系或故障定位；给出行为契约与必要快照。没有已知缺陷也允许返回空发现列表。
- **`propose`**：有明确接口、可独立验收的候选修复、测试或模块。先定义允许变化的行为与应保留的旧行为，再选择快照。

不要因一个任务较复杂就整体拒绝委派；先拆出局部、可证伪的交付物。若收集上下文和核验的成本已超过直接完成，就由主代理处理。

## 中等任务如何持续分工

主代理先确定必要接口、项目约定、当前基线和独立验收方式，再委派一个可以完整检查的工作包。规模取决于耦合和可验证性，不只取决于行数；例如一个解析/转换模块、一组边界清楚的表单逻辑、一个保持接口的局部重构，或围绕明确契约的一组回归测试。跨系统架构取舍与最终集成继续由主代理掌握。

| 当前需要 | 给 DeepSeek 的交付物 | 主代理同时推进或随后验收 |
| --- | --- | --- |
| 接口已确定，需要模块实现 | `propose`：实现文件、必要测试候选和简短说明 | 检查调用方、独立构造关键边界、审阅并执行测试 |
| 已拿到失败日志或复现 | `inspect`：可区分的故障假设；原因足够明确时直接 `propose` 修复 | 验证复现与因果，运行新旧行为回归 |
| 行为不变的局部重构 | `propose`：目标文件映射、候选差异和兼容性要点 | 核对最新基线、接口与回归结果 |
| 实现完成，缺有价值的测试 | `propose`：可运行测试文件，预期关联到契约 | 独立核验预期，检查测试能否检出错误变体 |
| 新需求影响已接受的候选 | 新快照和明确需求下的修订候选 | 检查需求差异并验证旧行为仍满足保留要求 |

这是按需求选择的分工示例，不是每个任务都要经历全部阶段。开始新阶段、收到测试反馈或发现新证据时重新考虑委派；一次已完成的调用不会关闭后续协作。可直接让 DeepSeek 实现已有清晰契约，不必先额外调用一轮计划或审查。独立工作可以后台进行，存在依赖的工作在前置结果核验后再派发。

对中等实现，要求 `mode: "propose"`、适当的 `taskType`，并在指令里明确候选文件名、目标路径映射及使用 `helper_write_artifact`；只在最终回复解释实现不算交付文件。工具仅能创建平铺候选文件，用映射表达项目目录，不能要求它直接修改项目。时间字段通常留给自动预算；材料少但分析深时主代理可显式选档。`feedback` 及工作包名称写在现有字段内，不发明运行器不支持的阶段或调度字段。

例如：先委派分页状态模块的候选实现，主代理同时准备集成与独立测试；测试暴露契约违约时，给出精确反例并委派修订；实现验收后，如果另有一组需要语义判断的回归测试，再考虑交给它编写。若第一稿已满足要求且没有新工作，就直接完成，不为体现“持续协作”追加调用。

减少主代理额度消耗依赖于替代实际起草工作：主代理不同时从零重写相同模块，不反复阅读无变化的整份输出，只针对新差异和仍未验证的要点检查。独立验收并不要求重写候选实现，但关键预期不能由候选代码自身定义。若原生代理或主代理更适合高耦合决策，按能力选择；不要把同一任务默认同时发给多个模型。

## Harness 与 OpenCode 如何分工

默认 `backend: "harness"`；第二个独立工作包可显式选 `backend: "opencode"`。两路具有相同的三种权限模式，每路仍由主代理发起，不能自主交换材料、再委派或直接合并项目。适合并行的例子是接口已确定的解析模块候选和独立的格式校验模块候选；主代理同时准备集成。与实现同属一模块的测试可以另包起草，但输入应是独立行为契约，测试预期仍由主代理核验，不能把两个模型回答一致当作正确性的证明。

在指令里分别写清交付文件映射、共同基线、接口和不得修改的部分；每路用独立请求、结果与候选目录。包之间存在依赖时，先核验前一包，再派发后续包，不让后一包猜测尚未产出的接口。采纳前比较各候选的快照与当前基线，按依赖顺序集成。

反馈可以继续交给原后端，各路不受一次调用限制；同一交付物的同一纠错上限不会因换后端而重置。账号或协议失败先诊断，不自动重派另一后端。只有一个值得委派的工作包时就只用一路，不为保持并发而复制实现或增加复审。双进程可以重叠运行不等于整体一定更快，实际收益需要计算委派、核验与返工成本。

## 请求里写什么

按实际风险取用以下信息，不必把每次请求扩展成固定表格：

1. **目标与边界**：要解决的问题、明确提供的事实、相关文件及不涉及的部分。
2. **行为契约**：接口、默认参数、边界语义、错误处理；区分现有要求、本轮新增要求与尚未决定的问题。
3. **交付形式**：发现列表、JSON、候选文件或简短比较；说明必需字段及可接受的空结果。
4. **判定依据**：什么证据可以支持结论；主代理将怎样检查。独立预期值、答案键或隐藏测试无需交给辅助代理。
5. **不确定性**：缺材料时指出具体缺口；不能把假设写成观察事实、把候选代码写成已运行，或将建议变成既有需求。

优先要求少量可验证的高价值发现。不要为了“全面”强制凑出缺陷数量、修复建议或额外解释。

## 按交付物补充要求

**机器可读 JSON**：明确顶层类型、必需键、允许值、重复与排序规则；要求最终公开回复只包含一个合法 JSON 值，无 Markdown 围栏、前后说明、注释或尾随逗号。数量、成员完整性与格式是不同要求，分别写清。只有业务需要时才限制额外键。

**代码审查**：每个发现关联文件 ID、原始快照哈希和行号，给出触发条件、实际行为、契约要求及最小反例。行号只说明位置，不能代替缺陷证明。把“确定缺陷”“待验证假设”“可选改进”区分开。

**故障分析**：给出最少的候选原因及区分它们的观测或实验；明确每条假设依赖哪些尚未确认的条件。没有证据支持的副本、缓存层或并发模型不得写成已存在的事实。

**候选实现**：说明允许修改的接口与行为、必须保持的兼容性、候选文件名和验证重点。让它标明未执行测试，不自行扩展输入限制或新增错误语义。依赖安装和真实项目应用仍由主代理决定。

**测试设计**：要求每个预期说明来自哪条契约；未知行为列为待确认，不编造答案。可让它提出错误变体或反例，但不得用候选实现的输出直接定义正确预期。

**方案比较或摘要**：要求来源可追溯，区分原文事实、计算结果与推断；未证实计划不能改写成已完成状态。硬约束计算由主代理复算。

## 一个审查请求的写法

把下列内容适配后放入 `instruction`，具体契约与材料放入 `input/files`：

> 审查所给快照中的重试行为是否符合输入契约。只报告能关联到契约的缺陷；无缺陷可返回空列表。每条发现提供文件 ID、哈希、行号、精确输入（含默认参数）、当前结果和契约预期。证据不足的项单列为假设。不要把可选改进当作缺陷，不新增未规定的输入拒绝规则；所有代码和测试均未执行。

若下游要解析 JSON，再补充具体字段与“仅一个 JSON 值”的限制；普通人工审查无需强行使用 JSON。

## 反馈续作

由主代理创建新请求与新会话，在 `feedback` 中提供：

- 一个已核验的反例：精确输入、实际结果、所需结果及依据。
- 要修正的交付部分，以及已确认正确、应保留的行为。
- 本轮新增需求或新快照；将需求变化与修复原违约分开说明。

对漏项给出集合差异或失败条件，对格式违约给出解析错误，对错误引用给出实际源码片段。无需复制整轮回复或私人会话历史。

反馈不能只说“再仔细想想”；新一轮必须有具体修正依据或清晰缩小的任务。对同一交付物的同一纠错目标，默认最多追加两轮；仍无进展、重复同一错误或核验成本超过收益时由主代理接手，不通过改名重置次数。这个停止条件不限制整个任务/对话的新工作包，也不要求无错误的交付追加调用。修订稿须重验原有正确行为，不能只验证新例子。
