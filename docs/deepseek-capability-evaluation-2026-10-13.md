# DeepSeek 受控辅助能力评估

评估日期：**2026-10-13**。固定模型：**DeepSeek-V41-Flash / Max**。运行环境：DeepSeek Harness **0.2.0-rc.2**、Node.js **24.19.0**、Windows；最大并发为 2。

**这次实测支持将 DeepSeek 用作能够深入参与局部工作的受控辅助代理，同时必须保留主代理的独立核验。** 它完成了局部实现、跨文件审查、测试设计和需求变更续作；也出现了机械提取漏项、严格格式违约，以及正确主结论旁边夹带错误解释和示例的情况。

本文是对本仓库辅助工作流的一次小样本评估，不是模型排行榜，也不提供通用正确率或与 Codex 的性能对比。所有“通过”都限定在给定题目与验收条件内。

3. **最后验证更新与安装。** 历史结果回放、检查器测试和安装后的 1 次真实委派用于验证新版工作流；它们不被追记为原评估的新独立题，也不证明模型自身能力提升。

因此，本文保留原评估中的失误，不用后续修正规则改写原始成绩。

## 方法与统计口径

### 如何出题与核验

- 共有 **12 个不同初测任务、2 次同题复测、1 次需求变更续作，共 15 次实际委派**。同题复测不算独立任务。
- 初测请求、预期答案和隐藏判定器在相应请求发送前固定，并记录哈希；评分后再次核对，输入没有变化。
- 模型只收到任务输入及明确提供的文件快照，没有获得答案键、参考实现或隐藏测试。
- 确定性题由独立脚本复算；缺陷按输入与契约复现；候选测试在正确实现及 6 个预先固定的错误变体上执行。
- 主代理和独立原生审查代理交叉核对人工判断。候选源码先审阅，再在带文件权限限制与 20 秒外部超时的 Node 子进程中运行隐藏测试，没有应用到真实项目。
- 分别记录调用完成、模型选择、核心正确性、引用与说明准确性、交付格式、用时和工具调用。成功调用或正确的主要结论不会使附加内容自动合格。

## 能力边界：保留失败的具体证据

### 1. 筛选题漏项，补齐内容后仍可能不守格式

T01 的完整预期与首轮回复可用以下最小比较确认差异：

```js
const expected = [
  'TASK-2', 'TASK-28', 'TASK-32', 'TASK-36', 'TASK-40',
  'TASK-42', 'TASK-48', 'TASK-50', 'TASK-52'
];
const actual = [
  'TASK-2', 'TASK-28', 'TASK-36', 'TASK-40',
  'TASK-42', 'TASK-48', 'TASK-50', 'TASK-52'
];
console.log(expected.filter(id => !actual.includes(id))); // ['TASK-32']
console.log(actual.filter(id => !expected.includes(id))); // []
```

预期来自对原始 45 条记录的独立筛选、去重和排序，不是让同一模型重新生成一个答案。上面的代码复现的是结果集合差异，并不替代原始筛选过程。

复测补齐了数组，却附加尾部文字。完整回复不能直接 `JSON.parse`。下面是该格式问题的简化演示，不是原回复逐字转录：

```js
JSON.parse('["TASK-2"]\nAdditional explanation'); // SyntaxError
```

实际工作中应分别检查格式与业务集合，不能只看条数、只解析正文片段，或把修补后的数据称作原始交付合格。机械筛选、去重、排序和精确计数优先交给确定性脚本。

### 2. 审查主结论正确，默认参数示例仍然可能错误

负对照题没有预埋缺陷。模型正确返回空缺陷列表，也正确说明默认 `maxRetries=3` 会在 `attempt=3` 停止，却随后写出“默认 attempt=3 → 800ms”。

以下为被审查函数，可作为独立 JavaScript 文件运行：

```js
function createRetryPolicy({ baseMs = 100, capMs = 5000, maxRetries = 3 } = {}) {
  if (!Number.isFinite(baseMs) || baseMs <= 0 || !Number.isFinite(capMs) ||
      capMs < baseMs || !Number.isInteger(maxRetries) ||
      maxRetries < 0 || maxRetries > 10) {
    throw new TypeError('Invalid retry configuration');
  }
  return function decision({ attempt, status, headers = {} }) {
    if (attempt >= maxRetries || (status !== 429 && (status < 500 || status > 599))) {
      return { retry: false };
    }
    const raw = headers['retry-after'];
    const trimmed = typeof raw === 'string' ? raw.trim() : '';
    const delayMs = /^\d+$/.test(trimmed)
      ? Math.min(capMs, Number(trimmed) * 1000)
      : Math.min(capMs, baseMs * 2 ** attempt);
    return { retry: true, delayMs };
  };
}

console.log(createRetryPolicy()({ attempt: 3, status: 500 }));
// { retry: false }
console.log(createRetryPolicy({ maxRetries: 4 })({ attempt: 3, status: 500 }));
// { retry: true, delayMs: 800 }
```

默认调用提前返回；显式改变 `maxRetries` 才得到 800 ms。引用行号正确不保证据此编出的示例正确，核验时必须保留精确实参与默认值。

### 3. 找到真实缺陷后，附加建议可能扩大契约

跨文件审查找全三类真实问题：相邻半开区间被误判冲突、幂等命中跨越租户、取消操作缺少归属检查。主要定位和修复方向正确。

但首轮附加文字将幂等检查描述为处在“任何校验之前”，实际已有字段及区间校验；又建议有效请求带额外字段就应返回 `INVALID_INPUT`，而题目没有禁止额外字段，执行也成功。

这些内容不能直接变成项目测试。测试应落实既有契约，不能悄悄新增模型偏好的限制。

### 4. 候选源码正确，变更说明不一定可靠

- **P01：** 时段合并实现通过隐藏测试，但说明将带额外属性的有效数组归为会拒绝的输入。实际代码接受这类数组，且符合契约。
- **P02-F1：** 新增并行轮次实现通过新旧测试，但说明错误引用了原优先级条件，还声称消除了旧代码并不存在的“相减精度问题”。

原优先级判断的实际形式为：

```js
best === null || node.priority > best.priority ||
(node.priority === best.priority && node.id < best.id)
```

它不是回复中错误描述的 `node.priority > best.priority && node.priority === best.priority`，原代码也没有用减法比较优先级。代码行为、源码引用和变更理由必须分别验收。

### 5. 表达不确定性也需要受证据约束

明确证据不足的题目中，模型正确保留候选原因，没有把相关性当因果。日志题的核心定位与原子写入修复也正确。

不过，日志题额外质疑题面已记载的写入是否真正发生，并引入副本过期读等未给出的条件；末尾压力测试也不足以独立区分守卫条件错误和原子性问题。合理做法是保留有依据的未知项，并设计能区分原因的检查，而不是用更多假设冲淡已知事实。

## 独立记录：监看组件问题

**原评估中 2/15 次出现 `monitor.available=false`，对应模型调用都已完成。** 两次分别发生在 `audit-uncertainty` 与 `review-multifile-bugs`：保存的监看状态仍为准备中或运行中，完成标记为假，其中一次仅有部分回复；两次均残留临时文件。

观察器写入链在捕获异常后停止保存，未保留异常详情。现有证据无法证明具体是写入、重命名还是文件占用导致。因此：

- 将它归为监看组件的可见性问题，不算 DeepSeek 回答失败。
- 面板滞后时，以本次委派结果 JSON 和进程状态核验完成情况，避免重复已完成的请求。
- 新版 Skill 已补充这一回退规则；该规则不等于底层监看写入故障已修复。

## 适用范围与公开材料边界

此轮支持的实际分工是：让 DeepSeek 参与指定文件的第二遍审查、局部故障假设、测试草案、明确约束的方案比较，以及有契约与独立验收测试的候选实现。主代理继续掌握材料选择、真实命令执行、项目修改、重要决定与最终验收。

本轮没有评测开放式研究、视觉或语音、长上下文、大型仓库集成、长期运行、压力下稳定性和自主执行；没有与 Codex 或原生子代理进行同题对照。小规模自建题及人工复核也存在覆盖和判断局限。

伪指令题仅验证了给定文本中的数据与指令分离。`text` 模式没有工具，其他模式也受应用层权限限制；没有越权行为不能证明模型在任意权限下都能自律，也不能外推为广泛安全保证。

本文根据本地保存的评估协议、结构化结果、公开回复、冻结哈希及测试记录整理。另提供 [15 次委派的机器可读统计摘要](deepseek-capability-evaluation-2026-10-13.metrics.json)，供核对统计口径。

为避免公开真实路径、会话信息和运行环境数据，仓库发布的是统计、关键证据与内联最小复现，**不包含原始日志、完整题库、答案键或全部隐藏判定器**。统计摘要也不是完整基准包。读者可运行文中 JavaScript 核对所示反例，但仅凭这些公开材料不能独立重跑全部 15 次委派；模型再次运行也不保证得到相同回复。

最终边界是：这份评估证明了若干具体任务上的可用性，也保留了已经发生的错误。新版 Skill 改进的是任务组织和验收流程，不能把它解释为模型能力升级或未知任务的可靠性保证。
