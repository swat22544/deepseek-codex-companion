# Harness 与 OpenCode 双后端接入验证

日期：2026-10-14（北京时间）。版本：Companion 1.1.0、Skill `2026-10-14-dual-backend`。本文验证接入与控制机制，不重算此前的 DeepSeek 能力评估分数，也不把用例通过数解释为日常正确率。

**结论：已安装的 Harness 与 OpenCode 两路均能受控调用并同时运行，但最终双路验收中只有 Harness 的交付可原样接受。** OpenCode 调用层成功，工具错误和交付不一致仍使其整体交付未通过验收。两种结果分别保留，不把修正文件存在或调用返回成功等同于任务正确完成。

## 环境与信任边界

Windows、Node.js 24、DeepSeek Harness 0.2.0-rc.2、OpenCode CLI 2.0.28。两路固定 DeepSeek Flash／Max，分别使用应用自身已经配置的认证；没有导出、复制或上传密钥。

两路是主代理调度的外部辅助进程，没有注册为 Codex 原生子代理线程。每个任务独立管理请求、会话、预算、快照、候选和监看记录。OpenCode 以私有配置目录和独占后台进程运行，禁用项目与外部技能发现。限制属于应用层控制，不构成操作系统隔离。

## 自动化与安装验证

1.1.0 的完整自动化测试 **122/122 通过**，并已安装到本地 Skill 与监看插件。测试覆盖后端路由、固定模型与工具边界、MCP 注册等待、结果机械检查、独立时间预算、子进程清理、公开流过滤、UTF-8 审计分块与结束边界、监看来源及旧记录兼容等。

安装后核对了 **35 个 Skill 文件、18 个插件文件**，与当前源文件一致；MCP 配置仅按安装器规则绑定本机 Node.js 与 Codex 数据根。两份 Skill 均通过结构校验，真实调用结束后未发现残留的 OpenCode 辅助工具进程。

自动化测试不需要模型账号，不产生真实模型调用；下文的真实联调与候选验收是单独的证据。通过测试不代表所有 OpenCode 版本兼容，也不能代替模型产物的独立核验。

## 真实验证

- 更新 Harness 认证后，原有 401 消失。短文本并行探针的两路均返回正确 JSON；两个调用进程有约 2.8 秒重叠，仅作连通性证据。
- OpenCode 的真实 HTTP 拦截验证了官方端点、`deepseek-flash`、`reasoning_effort=max`、启用 thinking 和流式响应。推理内容不写入监看，只记录活动数量；公开回复经增量流展示。
- OpenCode `propose` 完成了文件快照读取、文件清单读取和隔离候选写入。3 次模型请求、3 次工具调用均有相应记录；会话与 assistant 完成证据一致，候选未自动应用。
- 主代理审阅了其 `stableUniqueStrings` 候选，并独立验证首现顺序、大小写、空字符串、中文和 emoji、输入不变、冻结与跨 realm 数组、非字符串、稀疏空位及继承索引。217 次独立断言通过；这些断言只说明该小模块符合指定契约。
- 已安装的 Harness `propose` 生成 `isAsciiIdentifier` 候选。主代理独立检查非字符串、行终止符、Unicode、ASCII 字母数字和下划线，并扫描全部 UTF-16 单码元的首位／后续位行为，未发现契约违反。扫描次数不能折算成模型能力分数。
- 修复工具注册等待时序后，已安装的 OpenCode 完成真实 `inspect` 调用：两次模型请求、一次快照读取工具调用，返回指定模块的命名导出、是否改变输入、稀疏空位拒绝行为、大小写语义及示例结果。调用与实际运行证据通过，监看可用，结果与独立核验一致。

## 最终双路安装验收

在两条后端均已安装的状态下，同时分派两个不同工作包：Harness 审查 ASCII 标识符候选，OpenCode 根据另一份字符串去重候选产生五个指定测试用例。各自使用独立请求、会话、结果、候选目录与预算，没有向两路重复派发同一实现。

| 观察项 | Harness | OpenCode |
| --- | --- | --- |
| 权限模式 | `inspect` | `propose` |
| 调用结果 `ok` | `true` | `true` |
| 固定模型 | `deepseek-official / deepseek-flash / max` | `deepseek / deepseek-flash / max` |
| 模型请求数 | 2 | 5 |
| 受限工具调用数 | 2，均完成 | 4，其中 1 次因候选文件已存在被拒绝 |
| OpenCode 运行证据 | 不适用，按 Harness 协议核验 | `runtimeEvidenceVerified: true` |
| 超时 | 未触发 | 未触发 |
| 清理与监看 | 未报告未完成清理，最终监看可用 | 未报告未完成清理，最终监看可用 |
| 调用协议检查 | `protocol.ok: true` | `protocol.ok: true` |
| 机械检查 | 通过 | 未通过：存在工具错误 |
| 最终交付 | 审查结果通过独立核验 | 文件与要求及最终引用不一致，不能原样采用 |

两个委派进程存活时间重叠 **5887 毫秒**。该数值按外部委派进程生命周期计算，与单条结果中的任务预算计时口径不同；只证明两路确实同时运行，不是串行／并行耗时对照，也不表示提高了多少吞吐或节省了多少 Codex 额度。前面的约 2.8 秒来自较早的短文本探针，不能与这次数字相加或作为性能趋势。

Harness 审查正确识别了命名导出 `isAsciiIdentifier`，确认不强制转换非字符串、不接受结尾换行、接受下划线、不接受首位数字，并返回空缺陷列表。这些结论与已经独立检查的候选相符；空列表不外推为所有程序均无缺陷。

OpenCode 的原始委派要求按指定顺序交付五个用例，并将其中一个输入保留为 `["", ""]`。实际发生了以下过程：

1. 首次写入 `cases.json` 时，该输入被写成 `[""]`。虽然对应预期输出仍是 `[""]`，测试材料已经改变，不能算满足原契约。
2. 随后尝试写入同名候选文件，被“不能覆盖已有候选”的工具规则拒绝，产生一次 `status: "error"`。这次拦截符合预期，调用流程没有直接覆盖初版。
3. 改为另存 `cases.rev1.json`，将输入修正为 `["", ""]`。原始文件和修正文件都被保留。
4. 最终公开回复仍为 `{"artifact":"cases.json","caseCount":5}`，引用的是初版。修正文件存在不能让最终引用自动变正确；也不能在不说明的情况下将修正版替换成原始交付。

因此，OpenCode 本次调用的 `ok: true` 表示适配器与模型调用完成，`mechanicalOk: false` 则记录工具错误；交付层还存在指定输入与最终引用问题。整体交付没有原样采用，也没有为取得全绿结果继续反复调用。

主代理随后分别核对了两个文件的实际内容与记录哈希：初版第四组输入确实不符，`cases.rev1.json` 则精确匹配全部五组契约。修正文件是已经单独核验的部分，但该结论没有撤销工具错误，也没有修正原始最终回复对初版的引用。若采用修正版，需要明确指出选用了哪个文件；不能把这次双路原始交付改记为全部通过。

最终 Harness 监看保存曾遇到一次 `EPERM` 替换错误，有限重试后恢复，`failedFlushCount` 为 0、`recoveryCount` 为 1，最终监看仍可用。这里只记录错误类别与计数，不把它推断成某个具体系统组件导致的问题。

## 联调中发现的问题

1. **本地插件入口必须是目录。** OpenCode v2 的显式插件路径直接指向 `.mjs` 文件会被忽略。现在为每次调用生成独立插件目录，导入已安装的 guard，并要求激活审计。
2. **MCP 默认 Code Mode 隐藏原生工具。** 关闭通用 `execute` 后，若仍保留默认 Code Mode，模型可能用文字模拟工具调用。现在明确配置 `codemode:false`；文字中的伪调用没有审计，不视为工具执行或文件交付。
3. **MCP 工具连接与首次模型请求存在启动竞争。** 首次工具目录读取可能早于异步发现完成；在后续 context hook 等待已经太晚，因为执行器此前取得的权限快照没有这些工具。现在改为在 prompt hook 准入阶段触发 MCP 发现并等待所需工具注册，等待受本次截止及注册窗口约束；请求发出前仍核验完整工具清单，缺少则失败。修复后真实 `inspect` 读取与审查成功，没有通过放宽工具清单消除错误。
4. **分页不能同时携带 cursor 与 order。** 已修正为首轮排序、后续仅按 cursor 翻页；不能把 CLI 退出或一段回复替代全部完成证据。
5. **审计分块可能切断 UTF-8 字符。** 已使用流式严格解码，最终读取拒绝半行与残缺字符。公开中文不再因读取边界损坏。
6. **清理需要核对本次 MCP 子进程。** 通过受信审计中的 PID 核对退出；不能因 MCP 清理成功覆盖主进程原有的清理失败，也不会终止共享桌面服务。

开发时的失败记录保留原样，不改写为成功。工具缺失拦截发生在模型发送前，不代表 DeepSeek 服务连接失败。实际输出仍须经过主代理的格式、事实、代码、引用和测试预期核验。

本文只发布去除运行环境信息后的事实、聚合数量及必要的小型反例；原始请求、结果、会话标识、机器路径、完整审计与监看访问凭证均留在本地。

## 适用范围

真实小型任务验证补充了自动化协议与边界测试，但未执行长达四十五分钟的真实模型任务，也没有做串行／并行吞吐、服务限流或 Codex 额度消耗的对照实验。是否提高效率取决于工作包独立性、上下文、候选可采纳程度与复核成本。

建议在有两个可独立验证的工作包时，Harness 与 OpenCode 各承担一路；有依赖则先验收前一包，再派发后一包。不把同一实现重复派发给两路，不因切换后端重置同一纠错目标的轮数。
